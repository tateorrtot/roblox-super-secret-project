# The cold review of 2026-11-21

The user asked for "one more round" before the code went to an outside auditor: "what would i say about this code with no prior context if i were reviewing it and how are good roblox games archtiected". Eight readers on Sonnet each took one scope: the rules, the server and client scripts, Roblox's own traps, how shipped Roblox games are built, a skeptic who ran probes, the whole folder as a newcomer meets it, the two libraries, and the tests. A second reader tried to refute each finding marked serious or moderate, and ran the cases that run outside Roblox.

- **These readers are Claude's own helpers.** The user's words that day: "claude kinda was the same set of eyes on everything". This is not an independent review.
- **Found:** 87 findings. Several readers found the same fault, so the faults are fewer: that nothing is saved is 5 of the 87.
- **Second reading:** 42 findings went to a second reader. 35 were confirmed, 7 confirmed in part, and none refuted.
- **What each came to:** 16 mended, 2 refuted by a run in studio, 15 sent to the library's own session, 54 left.
- **The mends** are in commit 3678bdd of this repo, and each mend of the code has a test. `lune run tools/check` passes, and the play test passes 93 of 93.
- **What was left is mostly one of four things:** saving, which is not built; a fault in the structure, which waits on where the truth of a thing in the world is kept; a guard or a tuning, which the user's rule puts off until there is a game; and what is minor. The note beside each says which.

## Every finding, in full
### Reader: rules

The requires form a clean tree with no cycles, and World is the one hub: ten modules reach into it, and content scripts and requests also write to the plot and ground items behind its back. The most costly faults are structural: two registries that copy each other, request names built by reflection, a save module that nothing calls, and two modules that both write a player's open screen. The smaller faults are contracts a caller can break without an error (a clock that can run backwards, a script's item count trusted after its effect, one failing listener stopping the rest), and I only proved the clock one by running it.

#### RUL1. SaveData is never called, saves only the pack, and loses the whole pack for one retired item

- **Where:** `main-project/src/shared/save/SaveData.luau:27`
- **Severity:** serious
- **What:** Nothing under src outside shared calls SaveData.encode or decode, and the server has no DataStore code. Even if it were wired, it saves only the pack: the crate and stove state on the plot has no save format at all. The note on encode says an open screen's carried stack is not saved, so a caller that encodes before World.closeScreen loses that stack without any error. decode returns nil for the whole pack if any one stack names an item id that is no longer registered. I ran this: decode of {version=1, pack={slotCount=36, stacks={{slot=1,itemId='log',count=3},{slot=2,itemId='retired_thing',count=1}}}} returned nil plus 'pack: stacks[2]: no item has the id "retired_thing"'. The 3 logs go with it. The version range 1..CURRENT_VERSION is code for migrations nobody has.
- **Mend:** Either delete the module until persistence is real, or wire it to World.removePlayer and the server's player removal. In that wiring, call World.closeScreen before encode, and make decode skip and report unknown stacks instead of rejecting the pack.
- **Second reader: confirmed.** grep over src and tests finds SaveData only in save/SaveData.luau and tests/save/SaveData.test.luau, and src has no DataStore code. SaveData.encode calls only Inventory.encode(pack). Probe build/review-cold/refute-rules/p1.luau ran the decode case from the finding. It printed: nil pack: stacks[2]: no item has the id "retired_thing". The encode note says the carried stack is not saved. CURRENT_VERSION is 1 and nothing migrates.

#### RUL2. Every item and kind is registered twice, by copying one table into a second registry

- **Where:** `main-project/src/shared/content/Content.luau:19`
- **Severity:** serious
- **What:** Content.register copies each Item into ItemRegistry and again into ItemScripts, where the item is its own script. It copies each kind from PlacedObjectKinds into PlacedObjectScripts, where the kind is its own script. So Items, ItemRegistry and ItemScripts are three id-keyed tables for one thing, and PlacedObjectKinds and PlacedObjectScripts are two. The two registries disagree until Content.register runs. PlacedObjectKinds.get works on load, which the client uses at Main.client.luau:233. PlotRequests uses PlacedObjectScripts.find, which returns nil until register runs. ItemStack.new errors for every id until register runs. Tests work around this by re-registering by hand (tests/content/Stove.test.luau:34-36, tests/world/World.test.luau:27-28). A second register call raises an error.
- **Mend:** Keep one registry per concept. Let PlacedObjectKinds be the registry and move find, findOfPlacedObject and advancePlacedObjects into it, then delete PlacedObjectScripts' own table and the copy step. Do the same for ItemScripts once the item libraries arrive.
- **Second reader: confirmed.** Content.register (Content.luau:19-28) calls ItemRegistry.register(item) and ItemScripts.register(item.id, item) for each item, and PlacedObjectScripts.register(kind.PLACED_OBJECT_KIND_ID, kind) for each kind. PlacedObjectKinds builds kindsById at load, so PlacedObjectKinds.get works before register (used at Main.client.luau:233). PlacedObjectScripts.find reads scriptsByKindId, which is empty until register. ItemStack.new calls ItemRegistry.get, so it fails until register. Tests re-register by hand at Stove.test.luau:34-36 and World.test.luau:27-28. A second register raises an error. One small point: Items.ALL is a list, not an id-keyed table, so the three-id-keyed-tables count is slightly high.

#### RUL3. Client-callable request names are the keys of two tables, found by reflection

- **Where:** `main-project/src/shared/requests/Requests.luau:16`
- **Severity:** serious
- **What:** Requests.NAMES is every key of InventoryRequests and PlotRequests, and Main.server.luau:155 makes a remote for each one. Nothing marks a function as meant for clients. A server-side helper added to either table (for example PlotRequests.breakAll(world, player)) becomes a remote any client can fire with arguments of its choice. A non-function field would make carryOut call a non-function. Messages.luau:3 requires Requests just to get the names, so the client loads the whole request stack, World and GroundItems included, to learn a list of strings.
- **Mend:** Write the names as an explicit list (or a table of {name = function}) in Requests, with one test that every listed name exists and that no other function in the two modules is exported. Let Messages hold the literal list.
- **Second reader: confirmed.** Requests.luau:16-25 clones InventoryRequests, adds every key of PlotRequests, and takes NAMES from the keys. Main.server.luau:155 loops over Requests.NAMES with remotes[name].OnServerEvent. Nothing marks a function as client-callable, so a new exported function becomes a remote. Local functions are not exported, so only module fields are exposed. Messages.luau:3 requires Requests to build the list of names. The danger is latent: no such helper exists today.

#### RUL4. World.advanceTo lets the clock go backwards, so stoves replay time

- **Where:** `main-project/src/shared/world/World.luau:374`
- **Severity:** moderate
- **What:** elapsed is clamped to 0, but world.now = now is still assigned. The next advance then measures from the lowered time. GroundItems.luau:12-13 says the clock must only go forward, and nothing checks it. I ran this: a stove has 3 fish and 1 log, the world is at now=100, and I call advanceTo(110). After 10 s, 1 cooked fish is out and the second is 2 s in. I then call advanceTo(100) and advanceTo(106). The stove now holds 2 cooked fish and the fire is out, after only 10 real seconds. NaN is also accepted: after advanceTo(0/0), now is NaN until the next call.
- **Mend:** Use world.now = math.max(now, world.now), and either assert on a non-finite now or ignore it.
- **Second reader: confirmed.** World.luau:373-374: elapsed = math.max(now - world.now, 0), then world.now = now. Probe p4.luau, with a stove holding fish 3 and log 1 at now=100: advanceTo(110) gives fish 2, no fuel, cooked_fish 1. advanceTo(100) leaves the stove unchanged and sets now=100. advanceTo(106) then gives fish 1, cooked_fish 2, and the fire out after 10 real seconds. advanceTo(0/0) leaves world.now as NaN.

#### RUL5. A script's item cost is taken after the script has acted

- **Where:** `main-project/src/shared/requests/PlotRequests.luau:48`
- **Severity:** moderate
- **What:** interactWithTile(world, x, z) runs and places the object first. Hotbar.takeFromSelectedSlot then takes whatever number came back. The doc on that function says it raises an error for a negative number or a fraction. The ItemScript contract on ItemScripts.luau:17 says 'takes none from anywhere'. A script that places an object and returns -1 (or 0.5 for a stack of 4) leaves the object on the plot and raises an error with the item still in the hotbar: a free placement. A script returning 0 after acting is also a free placement. CrateItem and StoveItem return 0 or 1, so nothing breaks today.
- **Mend:** Have scripts return a boolean 'used one', and have the request take exactly 1 after a true. Or check that the count is a whole number from 0 to the stack's count before the script runs, by splitting a canInteract from an interact.
- **Second reader: confirmed.** PlotRequests.luau:77 passes the call interactWithTile(world, x, z) directly as the argument of Hotbar.takeFromSelectedSlot, so the script runs first. Probe p5.luau used a script that places a crate and returns a chosen number, with a stack of 4. For -1 and for 0.5, pcall failed with ItemStack:85 "holds 1 to 4, not -1" (and not 0.5), yet the plot held 1 object and the stack was still 4. For 0, the plot held 1 object and the stack was still 4, with no error. The code's own Note on this function admits the number is not checked. CrateItem and StoveItem return 0 or 1, so nothing breaks today.

#### RUL6. Two modules write a player's open screen, and a leftover stack can be dropped

- **Where:** `main-project/src/shared/players/PlayerState.luau:91`
- **Severity:** moderate
- **What:** player.screen is written by PlayerState.openScreen and closeScreen. World keeps a mirror of which placed object each screen is on (placedObjectIdsByScreen, World.luau:48, 226, 270). InventoryRequests.openPack (InventoryRequests.luau:157) calls PlayerState.openScreen directly, bypassing World. PlayerState.closeScreen returns the part of the carried stack that did not fit, and a caller that ignores it loses those items. A direct call also leaves a stale entry in World's table, because the table is keyed by screen and nothing else clears it. Only World.closeScreen does both jobs, and nothing stops a caller from using the other path. Fields such as player.screen and player.character are also plain assignable fields.
- **Mend:** Make World the only caller of PlayerState.openScreen and closeScreen. Route openPack through a World.openPackScreen. Keep placedObjectId in the screen table itself so there is nothing to mirror.
- **Second reader: partly.** The shape is real. InventoryRequests.luau:157 calls PlayerState.openScreen directly. PlayerState.closeScreen returns leftover (PlayerState.luau:91). World.placedObjectIdsByScreen (World.luau:50) is a mirror keyed by screen. The concrete failures are not in the code today. openPack runs only when canOpenScreen is true and opens the pack alone, which by the field's own comment has no entry in the mirror. The only caller of PlayerState.closeScreen is World.closeScreen (World.luau:227), which clears the entry and spawns the leftover. A stale entry or a lost leftover needs a future direct caller. This is a latent design risk, not a present bug.

#### RUL7. Pushing a ground item out of a tile respawns it, which resets its life and pickup delay

- **Where:** `main-project/src/shared/world/PlotCollision.luau:58`
- **Severity:** moderate
- **What:** pushGroundItemOutOfTile reads groundItems.itemsById[id].position directly, removes the item, and calls spawnStack with the world's now. The item gets a new id, a new spawnTime and a new 1.5 s PICKUP_DELAY. A stack that was 299 s into its 300 s life gets 300 s more when a stove is placed on it, and cannot be picked up for 1.5 s. World.luau:337 also reaches into itemsById. The doc admits the new id but not the lifetime reset.
- **Mend:** Add GroundItems.moveItem(id, position, velocity), which keeps stack and spawnTime, and use it here. Add GroundItems.getItem so callers do not read itemsById.
- **Second reader: confirmed.** PlotCollision.luau:58-70: pushGroundItemOutOfTile reads groundItems.itemsById[id].position, calls GroundItems.removeItem, then GroundItems.spawnStack(..., now). spawnStack gives a new id and spawnTime = now. removeExpiredItems (GroundItems.luau:294) and the pickup delay (line 254) both measure from spawnTime, so life and the 1.5 s delay restart. The doc says "spawns its stack again at the time now, as a new ground item with a new id" and does not say what that does to the item's life. World.luau:337 also reads itemsById directly.

#### RUL8. One failing listener or script stops everything after it, every tick

- **Where:** `main-project/src/shared/requests/PlacedObjectScripts.luau:84`
- **Severity:** moderate
- **What:** advancePlacedObjects runs advance for each placed object in id order with no pcall. If the advance of placed object 5 errors, ids 6 and up never advance, on every 0.1 s tick. World.luau:381-382 has the same shape: an error in any timePassed listener skips removeExpiredItems, so ground items stop expiring. The doc comment on each admits it. The wiring between timePassed and advancePlacedObjects is done outside shared (Main.server.luau:66-68). A world built without that line silently never cooks.
- **Mend:** Wrap each advance in pcall and warn. Move removeExpiredItems before the Signal.fire. Or have World own the call to advancePlacedObjects so there is one hook instead of two.
- **Second reader: confirmed.** PlacedObjectScripts.luau:84-91 calls advance with no pcall, and its comment says an error passes out and no later placed object is told. Signal.fire (Signal.luau:30-35) calls each connection with no pcall. World.luau:381-382 fires timePassed before removeExpiredItems, and the Note at lines 370-371 says an error skips the step after timePassed. The link between timePassed and advancePlacedObjects exists only in Main.server.luau:66-68 and in test helpers such as Stove.test.luau newConnectedWorld, so a World built without it never advances stoves.

#### RUL9. Crate and Stove copy the same code, and the item id is written three times without a link

- **Where:** `main-project/src/shared/content/Crate.luau:86`
- **Severity:** moderate
- **What:** Crate.breakPlacedObject (86-92) and Stove.breakPlacedObject (253-259) are the same five lines. getCrate and getStove, and Crate.get and Stove.get, are the same code. CrateItem.luau and StoveItem.luau are the same 20 lines. The string "crate" appears as Crate.PLACED_OBJECT_KIND_ID (Crate:27), Crate.ITEM_ID_WHEN_BROKEN (Crate:33) and CrateItem.id (CrateItem:10), with nothing tying them together.
