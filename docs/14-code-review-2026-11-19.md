# 14. Independent review of the code written overnight (2026-11-19)

Four agents each read the night's later code through a different lens and reported what they found wrong, with a scenario for each. A second agent for each lens then tried to refute those findings, running the code under Lune where it could. All eight ran on the Sonnet model. The code reviewed: `World`, `Station`, `RecipeRegistry`, `InventoryRequests`, the later functions of `InventorySession` and `Inventory`, and everything in `src/server` and `src/client`.

What follows is each finding in the reviewer's own words, whether the second agent upheld it, and what Claude did about it. The rules can be run outside Roblox and were; the server and the player's machine cannot, so findings about them were reasoned from the code and from Roblox's docs.

**The short of it.** The rules came through clean: the reviewers' own fuzzing found no way to make or lose an item, to raise an error with anything a player's machine can send, or to make a station behave differently in one long step than in many short ones. Fourteen findings at the edges were upheld. Thirteen were fixed, and one was left on purpose and written down.


## The rules keep their promises

**What the reviewer tried and could not break.** I found no real rules bug. I wrote three Lune scripts in build/review/ and they all came back clean.

- **Whole-world fuzz (`fuzz1.luau`):** 150 seeds of 3000 random operations each, with 3 players on a shared plot. It mixed every World request with garbage arguments, steps, moves and removals. After every operation it checked that stoves, crates and unrelated items never changed, that fish plus cooked fish and apple plus baked apple were conserved, and that logs never increased. It also checked that slot rules held in every stove and that `openedPlacedId` and `session.other` stayed consistent. No station record ever outlived its placed item.
- **Garbage arguments (`garbage.luau`):** 351,000 `World.answer` calls with a product of NaN, inf, negatives, 1e300, strings, tables, functions and booleans across all 13 request names. The sessions were open on a stove, on a crate and on the pack alone. None raised.
- **Long vs short steps (`fuzz2.luau`):** 4,000 random stations stepped once for the total time and again in many short steps. Their slots, burn time and work time always matched.

Slot rules also held by reading the code. Every route into a stove goes through `takes`, and I found no route that puts a wrong item in the fuel or output slot. Reading `Station.step` showed no infinite loop.

Two behaviours are documented, so I did not report them:

- Dropping into an existing ground item resets its timers, but it is capped by stack space.
- A step landing exactly on fire-out keeps progress that the next step then discards.

I also did not report time running backwards, because the contract forbids it.

### One non-finite character position makes tellPosition raise, so World.step is never reached

- Where: `src/server/Main.server.luau`, line 98 at the time. Kind: risk. Reproduced by the reviewer: no.
- The scenario: The rules raise on a bad position, as documented. `World.setPlayerPosition` with x = NaN or +-inf, or a NaN dropPosition, raises (reproduced in build/review/nan.luau). In Main.server.luau, `tellPosition` calls it with no pcall. `step()` calls `tellPosition` for every player before `World.step`, so one player whose HumanoidRootPart reports a non-finite position raises on every Heartbeat. Stations stop burning, ground items stop expiring, and no screen closes for anyone. The same raise also happens inside every remote handler. I could not check whether Roblox can ever report such a position for a replicated character, so this is a risk and not a reproduced bug.
- The second agent: upheld. The rules raise exactly as documented, and the server script does not guard the call. The chain is real, but whether Roblox ever supplies such a position is unverified, so it is a risk and not a known live bug. The fix is cheap and the failure would hit every player, so it is worth doing: treat a non-finite root.Position as no living character (setPlayerPosition(..., nil)), or pcall the per-player call inside step(). The user also suggested preferring existing plugins and libraries where they exist. Nothing here replaces this small guard, so that does not change the fix.
- **What was done.** Fixed. A position that is not a real place is treated as no character, and the per-player work is tried separately.


## The server, and a hostile or unlucky player

**What the reviewer tried and could not break.** I wrote a fuzz script, build/review/fuzz.luau. It sent 200,000 hostile `World.answer` calls (NaN, infinity, 1e300, tables, wrong types, bad sides and slots) from three players, interleaved with steps and moving positions. The calls hit a real crate with 40 crystals and a stove. Nothing raised, and item totals for fish, log, stove and crate matched what was put in (crystal was only the 40 in the crate), so I found no dupes or losses. The join, leave and respawn orders in Main are guarded (the duplicate-PlayerAdded check, `livingRoot` handling a missing root or a dead humanoid, requests ignored for players not in `world.players`, and `lastSent` cleaned on removal). Ground and plot parts are destroyed when their records go. Nothing but the player's own pack and screen is sent to a client, and the encoded tables are dense arrays.

### Every request does the full per-request work, with no rate limit, so one client can saturate the server

- Where: `src/server/Main.server.luau`, line 135 at the time. Kind: risk. Reproduced by the reviewer: no.
- The scenario: An exploiter loops `remotes.openPack:FireServer()` (or `closeInventory`, `selectHotbarSlot`, `usePlaced`) as fast as the network allows. Each message runs `tellPosition` (two raycasts, two `Players:GetPlayers()` loops, a new RaycastParams), `World.answer`, then `show()`. `show()` scans every ground item and placed item, and runs `HttpService:JSONEncode` on the pack and screen of every player in the server. With about 12 players that is roughly 12 encodes per message, so a few thousand messages a second keeps a server thread busy and lags everyone. `askForInventory` is cheaper to send but makes the server resend the whole pack each time. It should do nothing if the client already holds the latest state. Nothing counts or limits requests per player. I could not run this under Roblox, so the cost is reasoned, not measured.
- The second agent: upheld. The mechanism is real. How bad it is depends on how many players are present, and it is not measured. Server-wide show() on every request is the costly part: a request could update only the requester and leave the rest to the 10 Hz step. It is a hardening item for before a public test, not a bug that blocks the current testing.
- **What was done.** Fixed. The server shows the World at most once a frame however many requests arrive, and ignores more than 60 requests a second from one machine.

### A placed item can land on the spawn pad, so a joining or respawning player can spawn inside a solid 4-stud cube

- Where: `src/server/world/PlaceholderWorld.luau`, line 93 at the time. Kind: bug. Reproduced by the reviewer: no.
- The scenario: The plot slab is centred on the SpawnLocation, so the 12x12 pad overlaps tiles x and z 8 to 11, which is 16 tiles. `World.placeSelected` only refuses a tile if a player is standing on it right now (`isTileStoodOn`). Player A places a crate on tile (9,9) while nobody stands there. Player B joins or respawns and Roblox picks a random point on the pad, so about 1 in 9 spawns lands inside the anchored, collidable cube, which runs from y 0.4 to 4.4 and overlaps the pad top at y 1. B is wedged or ejected by physics. A griefer filling the 16 tiles makes every spawn land in geometry. `restock` already keeps ground items at least 9 studs from the spawn, but placing does not. It should refuse tiles over the spawn pad.
- The second agent: upheld. This is a real gap and cheap to close: refuse placement on tiles that overlap the spawn pad. Any player can do it today because the plot is shared. How the character resolves the overlap is unverified, but it is not safe to assume it is harmless.
- **What was done.** Fixed, for the placeholder: the plot now lies beside the spawn pad, not under it. A real map will need its own answer.

### The server step, `show()` and the handlers have no error isolation, so one raise stops the work for everyone

- Where: `src/server/Main.server.luau`, line 171 at the time. Kind: risk. Reproduced by the reviewer: no.
- The scenario: `step()` calls `tellPosition` for each player, then `World.step`, `restock` and `show()` with no pcall. If `tellPosition` raises for one player, `World.step` is skipped for everyone. `World.setPlayerPosition` raises on a non-finite position, and `Workspace:Raycast` can raise on a bad origin. No pickups, station work or ground-item expiry would run until that state clears. In `show()`, an error inside `sendInventory` (JSONEncode or FireClient) aborts the loop, so every player later in `Players:GetPlayers()` stops getting inventory updates. The same raise in a request handler also skips `show()`. I found no concrete trigger in the current data. The fuzz run (200,000 hostile `World.answer` calls) raised nothing and lost or made no items. This is a robustness gap, not a reproduced bug.
- The second agent: upheld. It is a robustness gap with no known trigger. A pcall around the per-player body and around World.step is a small change worth making when the server code is next touched, but it is not urgent.
- **What was done.** Fixed. Reading a position, stepping the World, restocking and telling each player are each tried separately, and a failure is warned of and does not stop the rest.

### Reach, standing-on and pickup checks use the position of a character the client controls, with no movement sanity check

- Where: `src/server/Main.server.luau`, line 99 at the time. Kind: risk. Reproduced by the reviewer: no.
- The scenario: `tellPosition` reads `HumanoidRootPart.Position`, but the client owns its character's physics. An exploiter teleports beside any tile, sends `hitPlaced`, `usePlaced` or `placeSelected`, and passes the `Plot.REACH` check from anywhere. It can also sweep up ground items by teleporting to them. With the shared plot this gives nothing extra. Once plots belong to players, it is how a stranger empties someone else's crate from across the map.
- The second agent: upheld. Real in principle, but the plot is a single shared one that anyone can already change, so nothing extra is gained. It becomes a real exploit once plots have owners, and the fix then is an ownership check plus a movement check. Accepted for now.
- **What was done.** Left, and recorded in CLAUDE.md under Claude's calls. Nothing is gained by it while the one plot is shared; it needs an ownership check and a movement check when plots have owners.


## The player's machine

**What the reviewer tried and could not break.** I read the whole client, `Messages`, and the server and shared request code the client talks to. I tried to break input routing and found it sound: `handledElsewhere` guards chat typing and button clicks, and Use and Hit are blocked while the screen is open. A press, drag or release of the right button is safe, and Hit is skipped when the camera turned. The furnace layout redraws correctly between stove, crate and pack alone, because slots are resized and the layout is recomputed whenever the slot count or station flag changes. The per-frame follow connection is made once and disconnected in `hide`. `ItemLooks` has a row for every item in `ItemDefinitions`. Ground items and grid lines have `CanQuery` off, so they do not block the plot raycast. The first `inventoryChanged` is recovered by `askForInventory`, which also clears the server's dedupe.

### A shift-click counts as the first click of a double click, so the next plain click on that slot gathers instead of putting down

- Where: `src/client/Main.client.luau`, line 108 at the time. Kind: bug. Reproduced by the reviewer: yes.
- The scenario: The player carries 4 apples (slot 13 picked up), then shift-clicks slot 12, which holds 5 apples. The apples go to another slot and slot 12 is now empty. Within 0.4 s the player left-clicks slot 12 to put the carried apples down. `lastLeftClick` was recorded by the shift-click, so `isDouble` is true and the client sends `doubleClickSlot`. The server's `InventorySession.doubleClick` sees a carried stack and an empty slot and gathers. I reproduced this with build/review/shiftdouble.luau: carried went from 4 to 9, every apple in the pack was pulled into the hand, and slot 12 stayed empty. The apples should have been put down in slot 12. The same stale record survives closing and reopening the screen, because `lastLeftClick` is never cleared then.
- The second agent: upheld. Real, small, and the fix is in one line. Do not record the click when shiftHeld is true, and set lastLeftClick = nil in setScreenOpen when the screen closes. The window is only 0.4 s and needs a carried stack plus a shift-click, so it will not happen often. It gives the wrong result in Minecraft terms (the hand should put the stack down).
- **What was done.** Fixed. The reading of clicks is now a rules piece of its own, `SlotClicks` (since renamed `SlotMouse`), with tests that include this case.

### ScreenScale never rescales if the camera does not exist yet when a screen is built, or if the camera is replaced

- Where: `src/client/ScreenScale.luau`, line 44 at the time. Kind: risk. Reproduced by the reviewer: no.
- The scenario: `ScreenScale.apply` reads `Workspace.CurrentCamera` once, while the hotbar and inventory GUIs are being built at script start. If it is nil then, `current()` returns 1 and no ViewportSize listener is connected. The panel and hotbar then stay at full size for the whole session, so on a 375 px phone the 900 px wide panel overflows the screen. The same happens if `CurrentCamera` is later swapped for a new Camera: the listener sits on the old one. It should shrink to fit the window.
- The second agent: upheld. Real in code but low-probability. Nothing in this project replaces the camera, and the camera is normally present when client scripts start. A cheap hardening later is to wait for CurrentCamera, or to listen to GetPropertyChangedSignal("CurrentCamera"). Not worth doing before the first phone test, and the phone test would show it at once if it ever happens.
- **What was done.** Fixed. ScreenScale now follows whichever camera there is, and every UIScale it made.

### Station.encodeView reports the old item's progress for a newly swapped input item until the next step

- Where: `src/shared/stations/Station.luau`, line 233 at the time. Kind: bug. Reproduced by the reviewer: yes.
- The scenario: Stove with 2 fish in slot 1 and a log in slot 2. Station.step(st, 4) gives worked = 4, so encodeView(st).working = 0.5. Then Inventory.setStack(inv, 1, apple x2), which is what a player's click does through World.answer. Before the next World.step, Station.encodeView(st).working is 0.667 (4 / 6, the apple recipe's seconds), while worked is still 4 and workingOn is still "fish". The comment says `working` is how far the work on the item in the input slot has got, which should be 0 for the apple. World.encodeView is called right after each answer and before the next step, so the client is sent a progress bar for work that was never done. Reproduced in build/review/a.luau.
- The second agent: upheld. Real but cosmetic and short-lived: the bar is wrong only until the next World.step. Cheap fix: in encodeView return 0 unless station.workingOn == recipe.input. Do not change the step behaviour.
- **What was done.** Fixed, with a test.

### World.setPlayerPosition does not raise for a bad dropPosition when position is nil, though the comment says it does

- Where: `src/shared/world/World.luau`, line 367 at the time. Kind: comment is wrong. Reproduced by the reviewer: yes.
- The scenario: World.setPlayerPosition(world, 1, nil, "junk") returns without error and ignores the second argument. The comment says it raises an error if position or dropPosition is given and is not a position. The early `return` for position == nil comes before the dropPosition check. So the caller's mistake goes unnoticed, and the drop position the caller meant to set is silently kept as the old one. Reproduced.
- The second agent: upheld. Real but trivial: a mistaken caller is silently ignored, and nil position with a drop position is a meaningless call anyway. Fixing the comment (a dropPosition without a position is ignored) is enough. Server code that calls it is trusted.
- **What was done.** The comment was changed to say what happens: a drop position given with no position is not looked at.

### The comment says one long Station.step ends as many short steps would, but the fire can still read as burning after short steps

- Where: `src/shared/stations/Station.luau`, line 149 at the time. Kind: bug. Reproduced by the reviewer: yes.
- The scenario: A stove with 1 fish and 1 log (burnSeconds 16). Station.step(a, 16) leaves isBurning false and burnLeft 0. The same stove stepped in 0.3 s pieces for the same 16 s total leaves isBurning true, with burnLeft about 1.2e-15. With 0.01 s pieces it is 1.4e-16. Floating-point residue is subtracted from burnLeft with no tolerance, while `worked` does use SAME_TIME. isBurning and encodeView().burning therefore disagree with the long-step result for one more step. A client that draws a flame from isBurning will show a fire that should be out.
- The second agent: upheld. Real, but the consequence is a flicker of isBurning for one step with a visually zero gauge; the next step burns the residue and relights as normal. The comment's promise of equality is slightly overstated (exact for items, within float error for times). Snapping burnLeft to 0 within SAME_TIME is a small optional fix.
- **What was done.** Fixed, with a test: a fire with next to no time left is out.

### The Station comment lists when work is lost but leaves out that a blocked output slot also wipes progress

- Where: `src/shared/stations/Station.luau`, line 22 at the time. Kind: comment is wrong. Reproduced by the reviewer: yes.
- The scenario: Fish worked for 4 of 8 seconds, then the output slot holds a full stack of cooked_fish or some other item. Station.step(st, 1) sets worked to 0 and workingOn to nil, because Station.recipe returns nil when the output has no room. The comment says work is lost only if the fire goes out for want of fuel, or a step finds a different item or none in the input slot. The input is the same fish and the fire is lit, so by the comment progress should be kept. After the output is cleared the fish starts again from 0. Reproduced: worked is 0 after the blocked step.
- The second agent: upheld. Comment wrong, behaviour arguably intended (pause vs reset is a design choice). Add 'or the output has no room' to the list. If the user prefers pausing, that is a design change, not a bug fix.
- **What was done.** The comment now lists it. Losing the work is what Minecraft does, and it was kept.

### The Messages comment says the inventoryChanged screen has three fields, but World.encodeView sends four

### The InventorySession header says every action that moves items returns how many it moved, but several return a boolean or nothing

- Where: `src/shared/inventory/InventorySession.luau`, line 35 at the time. Kind: comment is wrong. Reproduced by the reviewer: no.
- The scenario: The header says an action that moves items returns how many it moved. swap, click and doubleClick return `true` or `false`, and swapWithHotbar returns nothing, yet all four move items. Only pickUp, putDown, gather and quickMove return counts. The Inventory header makes a similar claim: a function given a count returns how many items it moved. takeFromSlot is given a count and returns a stack. A reader who trusts the header will write `if InventorySession.swap(...) > 0` and get a type error or a runtime error.
- The second agent: upheld. Real wording error, harmless because the type checker catches misuse of swap/click results. Reword the header to name which return counts and which return a boolean.
- **What was done.** Both headers were reworded to name which functions return a count, which a stack, and which whether anything changed.

### Station.step rejects infinity but its comment and message say any number of 0 or more is accepted

- Where: `src/shared/stations/Station.luau`, line 150 at the time. Kind: comment is wrong. Reproduced by the reviewer: yes.
- The scenario: Station.step(st, math.huge) raises "Station.step: seconds must be a number, 0 or more; got inf". Infinity is a number that is 0 or more, so the message contradicts itself and the comment 'Raises an error if seconds is not a number of 0 or more' does not mention that infinity is refused. The same wording appears in RecipeRegistry.register for 'seconds must be a number above 0', where math.huge is also refused. Reproduced for Station.step.
