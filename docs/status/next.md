# What comes next

1. **Get the user's read of the rewritten code, and after that their feedback on the game.** What the audits left is listed in `now.md`; none of it is urgent, and the screen's drawing code is best left until the user decides whether screens are made in Studio.
2. Carry on down the tree one piece at a time. For each: write the calling code first; build it with tests; then run the checks listed in `docs/code/conventions.md`.
3. Be sparing with agents. One overnight run used the account's whole usage limit. Reader tests are cheap (no tools). Do mutation and bad-argument checks in the session. Two small workflows on the Sonnet model (nine agents for the library survey, eight for the code review, a little under a million tokens each) ran on 2026-11-19 without trouble.
4. The plot, and Use and Hit, were built on proposals so that the user can judge them by playing. Their answer is needed before more is built on them: walls, things that cover two tiles, a plot of one's own, and how Hit works on a phone.
5. **Applying a click on the player's own machine before the server answers** is the next piece. The user chose it on 2026-11-20, as our own and not Roblox's Server Authority (`docs/research/18-client-first.md`), and asked that it sit on top as pieces of its own. The plan shown to them that day:
   - **One new piece on the player's machine, `Prediction`.** It keeps the last snapshot the server sent and the requests sent since, and gives the screen the snapshot to draw: the server's, with the unanswered requests carried out on it by the same `Requests.carryOut` the server uses.
   - **Each request goes up with a number,** and each snapshot comes down with the number of the last request it includes. The server sends when either has changed, so that a request it refused is still answered.
   - **What changes in what exists:** `Main.client` sends through `Prediction` and draws what it gives. `Main.server` reads the number and sends it back. `PlayerState` gets a way to be made from a snapshot. Nothing else in the rules changes.
   - **Order:** the hotbar, then the nine inventory requests that touch nothing but the player's own inventories, then the inventory half of a drop, then a look-alike part for a thrown stack.
   - **Not predicted at first:** placing, opening a placed item, and picking up from the ground. It is nearer than it was: the player's machine now holds a real `InventoryScreen`, decoded from each snapshot, and the requests are operations on it, so the same functions can be applied locally. It changes what crosses between a player's machine and the server (requests numbered, and each snapshot saying which request it follows), so its plan is shown to the user before it is written.
6. **The first process is built: the stove, as a furnace,** which is the form the user chose. What it cooks, how long it takes and what burns are placeholder content for them to change. Adding it took one new piece of rules (`Station`, with `RecipeRegistry`), slot rules in the inventory screen's rules, about fifty lines in `World`, and a furnace layout in the screen; no existing piece had to be rewritten.
7. First things to prototype on a real phone: the inventory screen by touch; handling and carrying; walking on a moving deck; an intercepted delivery becoming a real object; demonstrating a route by touch; a deck of a few hundred welded pieces.
