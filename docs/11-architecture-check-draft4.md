# Sign-off reader

**Would approve Part A:** no

I would not approve Part A as a whole. The owner can safely sign the shape: the six directories and their one direction (A1), where they live in Roblox subject to step 0b (A2), definitions as validated rows of components (A4), the check set (A8) and the place-file workflow (A9) once the small corrections listed are made; and he can let steps 0a to 2b go ahead, because they touch nothing contested. He should not sign "That is the whole kernel" or the sign-off rule as worded: at least seven capabilities that Part A itself relies on are missing from the table, and kernel-like code sits ungated in `lib`, `Features.luau`, the context and the shared glue, so the list is not one he can hold the author to. He should not sign A3's rules between features as settled (B4 itself plans to re-test them after 2e, and three of the nine steps of the foundation's own sequence, joining, leaving and returning, cannot be carried out from the rules as written), nor A6 and A10, where the saved-time rule contradicts A3 and B2, the timestamp, store name and key pattern are not stated, and a state broken by a failed action can be exported over a good save. Parts B and C do not undermine the shape; they contradict Part A only in details (glue that applies actions and makes decisions, a station that cannot use its own heat), and Part C leaves four questions that Part A has already answered without saying so.

## Problems found

### S1. "That is the whole kernel" is not true, so the sign-off rule cannot be held (blocking, part A)
- **Where:** A3, The kernel: "That is the whole kernel. A new kernel part needs the user's sign-off."
- **Problem:** Rules elsewhere in Part A use kernel capabilities the table does not list. (1) Check points: A3 says a later feature 'registers a check with the earlier feature', but A3 also bans module-level state in `rules` and requires state to be plain tables that survive saving, so the registered functions can only be kept by the kernel; no part is said to keep them. (2) Each feature's invariant check, registered in `install`, run 'after every action in every test' (A3) and after a load (A6). (3) 'Which of them a client may request' and the request shape glue checks against (A3, A5). (4) Making and removing an actor, and entities and their owners (A3 'when a player joins or leaves'). (5) A catch-up tick for one player with a time away and a cap (A6); `Ticks` is only 'the ordered list of features' tick functions, and the function that runs them'. (6) The load and unload actions `Save` must handle. (7) The kinds of act `Access` answers about, which the kernel cannot know because it 'knows nothing about any particular feature'. Kernel-like code also sits outside the gate: `lib/Defs` ('each feature registers the shape of its components', plus cross-row checks) with `Schema`, `Migrate`, `Signal` and `Clock`; `rules/Features.luau` with `build(content, options)`, which is the install contract plus an open `options` bag; the context, which 'carries ... the kernel's parts', so a field added to it reaches every state-changing function in every feature; and the shared glue of B3 (`Intake`, `Channel`, `Session`, `Actors`, `Instances`, `Loop`, `Persistence`; `Mirror`, `Events`, `Press`, `Aim`), which every feature's glue depends on and which has no sign-off rule at all. The gate counts files called kernel parts; an existing part can grow a new registry without tripping it. What is described is a small home-made framework (features register eight kinds of thing in `install` and are called back), which the note's own reference ('no framework') allows only if its surface is closed.
- **Suggestion:** Gate the surface, not the file list. Replace the sentence with: 'Sign-off is needed to add a kernel part, a row to "What a feature provides", a field to the context or to `options`, or a module that more than one feature's files require.' Add the missing rows (check points, invariant checks, actors) to the kernel table, and have the edge tool print the modules required by more than one feature and fail when one is not on the signed list.

### S2. The saved-time rule contradicts the tick rule and B2, cannot apply its cap, and never defines the timestamp (blocking, part across)
- **Where:** A6: "The document stores the time it was simulated through. On load each feature's tick is applied once for the time away, clamped at zero and at a cap." A3: "A tick reads state and applies actions. It takes time only from the kernel's clock." B2: "A station stores when its recipe started. The tick only looks for recipes whose finish time has passed". A10: "The meaning of the saved timestamp."
- **Problem:** A tick that takes time only from the clock has no input through which a time away could be 'applied once'. With B2's stored start times no special application is needed: the first ordinary tick after a load finishes any recipe whose finish time has passed. For the same reason the cap cannot work: after three days away the recipe still finishes. The only way to honour a cap with stored times is for the import to move them, which is not what A6 says. A station that would have run many batches while its owner was away completes exactly one, because the restart reads the clock. The time base of the kernel's clock (the server's Unix time, or time since the server started) is never stated, although the client must compute progress from the start time (B2) and A10 lists the meaning of the saved timestamp as expensive to change. The rule also settles question 8 ('the time away is applied on return') without saying that it depends on it, and the foundation has no other use for the timestamp.
- **Suggestion:** Replace the A6 bullet with: 'The kernel's clock is the server's Unix time in seconds. Features save absolute times. On load `Save` hands each feature's import the time away, clamped at zero and at a cap, and the import moves its saved times forward by the part beyond the cap. No tick is run specially. Depends on question 8.' In question 8, ask whether a station works through several batches for the time away or one.

### S3. No part or feature owns an actor: join and leave have no handler and an actor has no definition (major, part A)
- **Where:** A3: "Actions are applied by server glue for a request, by a tick, and when a player joins or leaves." A3 kernel table: "a table of entities (id, definition, owner)" and "`Save` | A player's document: asks each feature to export, import or unload" (step 7a). A4: "Every row has `stack`". A6: "all of them apply inside one load action".
- **Problem:** Step 3a must make an actor and a pack, and a player can leave from 3a on, but the only part said to import or unload is `Save`, built at 7a and 7b; until then nothing removes a leaver's state. A3's join and leave actions are never related to A6's load and unload actions. An actor is an entity, entities have a definition, and the one table of things requires `stack` on every row, so an actor has no definition; the pack's slot count and a new player's first document have no source, and invariant 5 forbids a rule from naming a definition for them. A5 also does not say what answers a Ready that arrives before the load has finished.
- **Suggestion:** Add a kernel row and three sentences: '`Actors` (or `World`): makes and removes an actor and runs each feature's load function in order and unload function in reverse; from step 3a. An actor is an entity with no definition. Joining is the load action with an empty document for a new player, and leaving is the unload action; `Save` at 7a only supplies the document. The pack's size is a number glue passes in the join payload from content. A Ready that arrives early is answered when the load action completes.'

### S4. "One id carried or placed" cannot hold for anything that stacks, and what counts as an entity is not said (major, part A)
- **Where:** A3, State conventions: "A thing keeps one id whether it is carried or placed. A crate broken into an item is the same entity." A4: "log = { stack = { size = 16 } }" and "Every row has `stack`".
- **Problem:** Part A never says whether a stack in a slot is an entity. Either way the rule fails for a placeable with a stack size above 1, which is what walls, floors and ceilings are in the agreed design: placing one from a stack of 16 needs a new id, and breaking it into a stack that already exists ends one. A5 gives stacks on the ground an entity id that likewise begins on a drop and ends on a pick-up. The rule is true only for an item of stack size 1, yet saving ('ids local to the document'), the wire ('messages carry entity ids') and `World`'s table all rest on it.
- **Suggestion:** State it exactly: 'Entities are actors, placed things, stacks on the ground, and carried items that have a container. Only an item with a container keeps its id when placed and broken; placing any other item makes a new entity and breaking it ends it. The validator requires stack size 1 on every row with `container`.'

### S5. Unload reports no records and load's records are unstated, so the screen cannot follow either (major, part A)
- **Where:** A6: "Unloading is its own action. Features unload in reverse order. Nothing is being broken, so no "removed" records are reported." A3 step 5: "`World` fires once with the whole list. Server glue listens there."
- **Problem:** Glue learns of changes only through the records `World` fires with. With no records on unload, nothing tells building's projector to destroy the leaver's Models, inventory's held-item projector to remove what was in the hand, or a sender to close the panel a visitor has open on one of the leaver's containers. For load the note says nothing: if it reports the ordinary 'placed' records, later features' reactions and the one-off 'placed' events fire for a plot that was only restored; if it reports none, no Instance is made.
- **Suggestion:** Add to A6: 'Load and unload report their own record kinds (loaded, unloaded), one per entity and per closed viewer. Glue treats them as it treats placed and removed; no feature reacts to them and no one-off event is sent for them.'

### S6. "Validate first" does not cover two changes in one earlier feature, and does not say where registered checks run (major, part A)
- **Where:** A3: "The handler validates everything first. It asks earlier features whether what it needs would succeed, and runs any checks later features registered with it." and "A function that can refuse comes as a pair: one that answers whether it would succeed, and one that does it." and "Its records are delivered in turn."
- **Problem:** (a) A pair answers one call against the present state. A recipe finishing takes inputs out of a container and puts outputs into the same one: 'would the outputs fit' is false until the inputs are gone, and two outputs can each fit alone but not together. The handler gets either a false refusal or a failure after the first change, where there is no rollback. The foundation reaches this at step 6b. (b) Checks are run by 'the handler'; if they do not also run inside the 'would it succeed' function, any later feature that calls down goes round a check a third feature registered. (c) Reactions may set off further reactions; nothing states the order or a bound.
- **Suggestion:** Add: 'A "would it succeed" question takes the whole list of changes the caller intends in that feature and answers for the list. Registered checks run inside that question, so a handler and a caller pass the same gate. Records are delivered in the order reported, from one queue, and `Actions` fails the action past a fixed count.'

### S7. After a failed action nothing says whether other reactions run, whether the state may be exported, or what a failed load leaves (major, part A)
- **Where:** A3: "There is no rollback. If code throws after the first change, `Actions` logs the action, still fires `World` with the records so far so the screen matches the state, and reports failure." A6: "`World` is the truth." and "If the stored version is newer than the server, or migration or validation fails, it ends the session leaving the data as it was, tells the player and removes them."
- **Problem:** (1) 'The records so far' implies delivery stops at the throw; then one feature's bug leaves every later feature out of step with a change that did happen. Glue listeners are 'protected from the others' failures'; reactions are not said to be. (2) Nothing stops `Save` exporting a state that a failed action left broken. That document fails validation on the next load, A6 then removes the player on every join, and the last good document has been overwritten: one thrown reaction becomes a permanent lock-out. (3) A throw or a failed invariant in the apply phase of a load is not covered, and partial state stays in `World`.
- **Suggestion:** Add to A3: 'A reaction that throws is logged and the remaining reactions still run.' Add to A6: 'Before every export `Save` runs the invariant checks for that player; if one fails it writes nothing, logs, and ends the session on the last good document. A failed apply phase is followed by the unload action and the same ending.'

### S8. The client cannot tell what a button press will do (major, part A)
- **Where:** A3 kernel table: "`Buttons` | Turns a button press into an action, given what is held and what is aimed at". A1 table: "`client` | `lib`, `content`, `protocol` | `rules`, `server`".
- **Problem:** The meaning of Use and Hit is resolved in `rules`, which the client may never require. Under question 1's three-level precedence the client cannot label the Use button, cannot know whether coal on a stove goes in or opens it, and cannot know whether to draw the placement preview or give way to the crate in front of the player. Either the precedence is written a second time in client code, where it can drift from the server's, or the one consistent control the owner asked for gives no hint of what it will do.
- **Suggestion:** Declare each feature's button meanings as data in its `protocol` file and put the pure matcher in `lib`; `Buttons` on the server and the client's preview and hint then run the same function. If no hint is wanted, say so in A3 and say the preview shows whenever a placeable is held.

### S9. No edge rules inside `server`, `client`, `lib` or the kernel, where most modules live (major, part A)
- **Where:** A1: "Finer rules, enforced by the same check: A feature in `rules` may require the kernel, features listed before it, and only its own file in `protocol`." A8: "It fails on any edge the rules in A1 and A3 do not allow". B3: "Client rules: a view never talks to another view".
- **Problem:** The finer rules cover only features in `rules`. B3 plans 20 server and 16 client modules against about a dozen in `rules`, and for those any require inside the directory passes the check: one feature's sender may require another's projector, shared glue may require a feature's glue, any glue may require any feature's rules. The one rule of this kind sits in Part B and is not an edge rule the check knows. The printout shows a web; nothing stops one. The finer rule also leaves out `lib`, which the table allows, and nothing says what the kernel may require or that it may not require a feature.
- **Suggestion:** Add to A1: 'A feature's glue (`server/<feature>`, `client/<feature>`) may require the shared modules of its directory, `lib`, `content`, its own `protocol` file and, on the server, `rules`; never another feature's glue. Shared glue never requires a feature's glue; only the entry script does. The kernel requires `lib` and no feature. A feature may also require `lib`.'

### S10. A request is refused by measuring to an Instance: a rule tied to the visual layer (major, part A)
- **Where:** A5: "If it fails for some feature, that feature's projector and view change, and so do aiming and the reach check for its things, which today read Instances. No rule changes." A3: "Anything Roblox knows that a rule needs, such as a position, arrives in the payload as plain numbers".
- **Problem:** Whether a request is honoured depends on an Instance a projector made, and Part A itself says the reach check changes when the projection changes. A11 notes that Roblox advises spreading a returning plot's Instances over frames; if that is done, for that time the state exists and the Instance does not, so valid requests are refused. The check is glue, so no test in A8 covers it. It also needs `server/inventory/Reach`, glue that applies a close action on its own distance check. A3 already gives the way to avoid all of this: the actor's position in the payload.
- **Suggestion:** State: 'Glue adds the actor's position to each request's payload. Reach is a rule: the handler measures to the thing's position in state (a grid's origin and tile, a ground stack's position).' Aiming stays on the client. If reach stays in glue, say so in A3's list of who applies actions and in A5's 'never decide', and make it fall back to state when the Instance is missing.

### S11. Part A does not separate what is signed from what is still a hypothesis (major, part A)
- **Where:** Where this stands: "Part A is what the user is asked to approve. It is the shape, the rules, and the decisions that are expensive to change." B4: "After 2e there is a real question to answer from the code, and I would stop there and revise this note: did "call down, react to records, validate first" hold up for a container that is opened, moved into, and removed?"
- **Problem:** The three rules B4 means to re-examine are A3's rules between features, the centre of what the owner is asked to approve. A5 calls solid things 'a hypothesis' and A11 lists the double mapping, the start-up order, Lune and the new solver as untested. A signature on Part A therefore covers at least five things the note expects it may change, and the one about A3 is admitted only in Part B. Testing the mechanism in code is the right answer to three failed drafts, but until the test it is not a decision.
- **Suggestion:** Put a three-row table at the head of Part A: signed now (A1, A2's layout, A4, A7, A8, A9); signed as a hypothesis with the step that tests it (A3's rules between features: 2e; A5's solid things: 4f; A2's live sync and start-up: 0b; A8's solver and Lune: 0a); not yet signed (A6 and A10: at 7a, after questions 3, 8 and 10).

### S12. A5 says the place settings are set by hand; A9 says Rojo syncs them (minor, part across)
- **Where:** A5: "Place settings, written into the project file and set by hand in the Studio place, because `StreamingEnabled` cannot be set by a script". A9: "Rojo syncs code, the two RemoteEvents and the place settings into it and leaves everything else alone."
- **Problem:** By A5's own reason Rojo's plugin cannot set them, so A9 is wrong for at least the streaming settings (Rojo's sync page says not every property can be synced live because of the Studio plugin API: rojo.space/docs/v7/sync-details, read in this run). The settings then live in two places, the project file and the Studio place that ships, with no check that they agree.

### S13. "An allowed edge nothing uses" cannot be a failure as written (minor, part A)
- **Where:** A8: "It fails on any edge the rules in A1 and A3 do not allow, on a file name whose case is not exact, and on an allowed edge nothing uses."
- **Problem:** A1 allows a feature to require every feature listed before it. If an unused allowed edge fails the check, `climate` must require `inventory`; if the allowed edges are a separate list, that is the hand-written table this draft says it removed. The owner also asked for diagrams, and the tool 'prints the module graph' in a form the note does not state.

### S14. A8 names modules and checks that A1, A6 and A9 do not line up with (minor, part A)
- **Where:** A8: "Tests | `lib`, `rules`, pure client modules | Lune". A6: "wrapped in a module of ours because it cannot run under the tests". A9: "A place built from the project file alone is used only by the checks."
- **Problem:** A1 has no class called pure client modules, and the purity lint and the no-Roblox-globals type check do not cover them, so nothing keeps them pure. A6 wraps ProfileStore so that something can run under the tests, but the code that uses the wrapper is server glue, which A8 does not test; the ordering of join, load failure and leave, the most fragile code in the foundation, is covered by no check but the type checker. No check in A8's table builds a place, and A9's pre-publish placeholder tool is not in the table. Nothing checks that each definition id has its model in `ServerStorage` and its row in `ThingLooks`.
- **Suggestion:** Give pure glue a place, for example a `pure` folder under `server` and under `client`, covered by the no-globals checks and the tests, and put the join, load-failure and leave ordering there behind small interfaces. Add rows to A8 for the two place-file checks, and let the place-file tool fail when a placeable definition has no model.

### S15. Two A3 claims rest on convention only, and one cannot be typed without a cycle (minor, part A)
- **Where:** A3: "It carries the actor, the way to report a record, and the kernel's parts." and "`World`'s own lookup returns an unknown type and only the owner calls it, so every use of another feature's state is a require the edge check can see."
- **Problem:** If the context carries every kernel part it carries `Actions`, which hands every handler and reaction the means to do what 'Handlers do not apply actions' forbids. It also cannot be typed: `Actions` creates the context, `Save` and `Ticks` need `Actions` to apply their actions, and A1 forbids cycles. For the lookup, 'only the owner calls it' is checked by nothing: any feature can call it with another feature's name and cast the result, and no require appears.
- **Suggestion:** Say: 'The context carries the actor, the way to report a record, `World`, `Access`, the definitions and the clock.' And: '`World` hands a section's accessor to the feature that registers it, once, at install; there is no lookup by name.'

### S16. A component's shape and type are declared twice, not once, and nothing compares them (minor, part A)
- **Where:** A4: "A component's shape and Luau type are declared once, in that feature's file in `protocol`" and "one test passes the real content through all of them" and "Luau cannot type-check a file that imports nothing".
- **Problem:** The shape (for the validator) and the Luau type (for the checker) are two declarations in one file. The validator checks rows against the shape, the type checker checks code against the type, and types are erased at run time (Appendix C), so a test that passes content through a typed function cannot see that the type says `slot` where the shape says `slots`. The last quoted sentence is also wrong as written: Luau does check such a file; what it lacks is the component types to check the rows against (the grounding's independent check shows annotated rows being checked for missing fields and wrong types).
- **Suggestion:** Add: 'The typed function builds the component field by field, never by a cast, and the test compares its result key for key with the validated row.' Reword to: 'Because `content` requires nothing, its rows cannot be annotated with the component types.'

### S17. Three A5 rules do not cover rows of A5's own table (minor, part A)
- **Where:** A5: "A projector builds the solid shape from the footprint"; "One-off events: a thing breaking, a recipe finishing | Sent by the owning feature's sender"; "`stations` marks a station as running on the Instance `building` made".
- **Problem:** Items on the ground and in the hand are in the table, but a thing with only `stack` has no footprint, so 'what a tap can hit' has no source in its definition. Nobody says which players receive a one-off event, though data sent by remotes has to be scoped by hand (grounding). A running station is told twice, by an attribute for everyone near and by the sender for whoever has the panel open, with no order between the two, and the table has no row that says which fact goes which way.
- **Suggestion:** Add: 'A ground or held item uses one fixed box set in content.' 'A one-off event goes to every player on the server.' 'What everyone nearby sees rides on the Instance; what only the viewer of a panel sees goes by sender.'

### S18. The restart rule is too narrow, and a rename has no stated path into a feature's section (minor, part A)
- **Where:** A6: "A release that changes the save format ends with a restart of servers running the old version." A4: "A rename is a row in a renames table that the save migration applies."
- **Problem:** A release that only adds a row of content has the same effect on old servers: a document saved with the new definition id fails validation there and A6 removes the player. That is safe for the data, but it happens on the commonest kind of release. For renames, each feature owns its own section's migrations and the document has one version number, so who applies a rename inside a feature's section, and whether a rename bumps the version, is not stated.
- **Suggestion:** Change to: 'Every release that adds or renames a saved definition id, or changes the format, ends with a restart of old servers.' Add: 'A rename bumps the document version, and `Save` gives the renames to each feature's decode.'

### S19. The stored owner can disagree with where a thing is (minor, part A)
- **Where:** A6: "Each entity records its owner, and a feature exports what belongs to the leaving actor."
- **Problem:** For a carried thing the owner is also implied by whose pack holds it. No rule says who rewrites the stored owner when a thing changes hands (a filled crate dropped by one player and picked up by another), and A7 has no invariant for it.
