# The double check of the code, 2026-11-20

The user opened the code for the first time on 2026-11-20 and could not judge it. They asked why `InventorySession` was seven hundred lines, why it was not just `Inventory`, what `SlotMouse` was, whether the code followed FoxFabric's standards, and whether it was "unmaintable spaghetti or not". They asked for the architecture to be explained and double-checked. This file is the record of the double check. `CLAUDE.md` holds what was decided from it.

## How it was done

- **Measured by script** (`tools/metrics.py`, and a one-off count of argument checks): lines, comment share, longest function and deepest nesting for every file in `src`.
- **Read by Claude:** `InventorySession`, `SlotMouse`, `World`, `InventoryRequests`, `PlayerState`, `Inventory`, part of `Plot`, and both `Main` scripts.
- **The user's template read word for word:** FoxFabric's `adder.gd`, its tests and demo, and both READMEs.
- **Five independent readers, each through one lens,** on the session's own model: a Godot developer who has never seen Roblox, shown seven files and nothing else; simplicity; responsibility and growth; the user's own standard; and the player's machine. A skeptic then tried to refute each finding of the last four. Nine agents, 3.2 million tokens, about an hour.
- **A sample:** `InventorySession` rewritten to the user's standard on the side branch `leaner-sample`, with the same public functions.

What this does not cover. Nothing was run in Studio. Where a reader offered replacement code, the reader and the skeptic ran it in memory against the project's tests, but none of it went through the formatter, the linter or the strict type checker, apart from the sample. Statements about how Roblox itself behaves come from its documentation or from this project's notes, not from a run.

## What every reader agreed on

- **It is not spaghetti.** What requires what runs one way and a tool checks it. A click reaches the inventory through seven calls in a straight line, none calling back up. Nothing a player's machine sends depends on the inner checks: with every inner `error()` switched off in memory, both tests that send 12,000 hostile requests still pass.
- **It is over-documented, over-checked and under-split,** and the cause is written down: the conventions in `CLAUDE.md` asked for a long comment on every file and function, an error naming the function for every argument that could be wrong, and readers who "predict its behaviour from its comments". Those conventions were Claude's, and they contradict the template they claimed to be drawn from. They were rewritten on 2026-11-20.
- **Two names told a stranger nothing:** `InventorySession` and `SlotMouse`. `World` and `Messages` told the Godot reader nothing either.
- **Three pieces do more than one job:** `InventorySession` (five), `World` (nine), and `Main.client.luau`, which holds about 70 lines of Use and Hit logic that no test outside Roblox reaches.
- **A check must stay at the bottom.** With all inner checks off, mistakes in our own code made or lost items with no error: a stack of -5, a stack parked in slot 37 that saving would drop, `addItems(-1)` removing a log. So the rule is not "check only at the edge". It is: check what comes from outside once, where it comes in, and keep one plain guard in the piece that owns the data (`ItemStack.new`, a slot of `Inventory`, a count in `Inventory`).

## Three bugs found by reading, none yet reproduced in Studio

1. **A stack dropped while facing a placed block lands on top of it and cannot be picked up from the ground.** The server picks where a drop lands with a ray that hits the block's top, 4 studs up, and picking up measures in a straight line from the ground under the player with a radius of 4. Standing on the block reaches it.
2. **The faint block is drawn on tiles where the server will refuse the placing,** such as the tile the player stands on. The player's machine applies reach and nothing else.
3. **While a lit stove is open, the whole pack is sent to that player about ten times a second,** because the gauges change at every step and the server compares the whole message.

Also: after a fire burns out, `Station.burnTotal` keeps the last fire's figure. It does no harm today.

## The sample

Branch `leaner-sample`, in the folder `build/leaner`. `InventorySession.luau` goes from 709 lines to 333 (374 code lines to 272, 301 comment lines to 28), with the same public functions. Its deepest nesting goes from 5 to 2. On that branch every check passes, and mutation testing catches 330 of 337 deliberate bugs; each of the other 7 is a change no caller can see. The 48 checks that went with the removed error messages are gone, and 9 checks were added: 320 became 281.

One reader's skeptic found a flaw that the first version of the sample shared: with no check on the hotbar's size, a session opened with a size the pack does not have could lose a stack in `quickMove`. The sample keeps that check as one line.

The findings follow as the readers gave them, shortened. `build/review-2026-11-20.json` has every finding in full with its replacement code, but `build` is not kept in git.

In their own words:

> First the overall shape, since it threw me. None of these seven files touch Roblox at all. They are pure-logic modules. Each one is a table of static functions plus a plain dictionary of data, and you call Inventory.addItems(pack, "log", 5) instead of pack.add_items("log", 5). Imagine every class in your Godot project as a GDScript file of static funcs that take a Dictionary as the first argument. No nodes, no signals, no _process. Some other code I wasn't shown (the server and client scripts) presumably creates the Roblox objects, calls these functions and redraws.
>
> Inventory vs InventorySession: Inventory is the container itself, a fixed number of slots holding item stacks, like an Inventory Resource. InventorySession is 'the inventory window is currently open'. It points at the player's pack and optionally one other container (a crate, a stove), owns the stack stuck to your cursor, knows which stove slots accept which items, and implements every Minecraft mouse rule: left/right click, double-click to gather, drag to spread, shift-click, number keys. When the window closes, the session is thrown away and anything on the cursor goes back into the pack. In Godot I'd call it an InventoryScreen controller. 'Session' made me think of networking or transactions.
>
> SlotMouse: client-side input recognition. It's fed raw mouse events (button down on a slot, pointer entered a slot, button up, click) and decides whether that was a click, a double-click, a shift-click or a drag over these slots. It then hands back the name of the request to send to the server. In Godot that's the gui_input code on the slot Controls, plus a double-click timer. The tricky part is that Roblox can report 'click' and 'release' in either order at the end of a drag.
>
> World: the whole server-side game state in one data object: the shared plot, items on the ground, every player by UserId with their position, every station's fire and progress, and the clock. It has addPlayer/removePlayer, setPlayerPosition, answer (route a client request, which is where all cheating is filtered) and step (the tick: auto-pickup, auto-close screens you walked away from, burn stations, despawn ground items). It's the model half of a model-view split. It is not the scene.
>
> Is it spaghetti? No. The dependencies run one way (World -> InventoryRequests -> PlayerState -> InventorySession -> Inventory -> ItemStack), and nothing reaches back up. But it's over-documented and under-split. About half of every file is prose that restates the code. Validation helpers are copy-pasted across files. Read-only fields are cast away with `:: any` to write them. InventorySession and World each do four or five jobs.

What they expected instead, coming from scenes and nodes:

> Coming from Godot I'd expect the responsibilities to be split along the things you can point at in the game. That would mean an Inventory resource that emits a `changed` signal (here the UI has to 're-read after changing'), an InventoryScreen scene whose slot nodes each handle their own input (which would absorb SlotMouse and the click/drag half of InventorySession), and a separate CursorStack or 'held item' object. A Player node would own its pack, hotbar and position together, instead of PlayerState plus World's WorldPlayer. Plot, Station and GroundItems would each be nodes that tick themselves in _process, so World wouldn't step them all and route every request. Each script would be under about 150 lines, with a two-line header comment instead of a design document, one shared validation helper instead of five copies of isWholeNumber, and fields that are simply writable instead of marked `read` and then cast to `any`. I'd also expect the code to show where the Roblox engine actually comes in (what plays the role of nodes and scenes, and how the server tells clients what changed), and none of these files show that. I'd also flatten the deepest nesting: gather, hitPlaced, step.

## Lens: Simplicity

Through the simplicity lens this is not spaghetti: requires run one way, the rules pass all 1,566 of their own checks, and most functions are short. It is over-armoured: 489 of the 2,080 code lines in src/shared (23%) re-check arguments passed between type-checked modules, and on one click the slot number is checked six times. That, with 301 lines of comment, is why InventorySession is 709 lines; with the re-checks, one unused function and one nested loop dealt with I measured 282 code lines instead of 374, and both hostile-input fuzz tests still passed. The cause is written down in CLAUDE.md (lines 194, 196, 200), where the author's conventions demand a named, caller-blaming error for every invalid argument, which conflicts with the owner's "simple and straightforward". All nine deeply nested functions flatten to depth 2 by naming the inner step, and four workarounds need a decision: stacks validated and copied at every hand-over, `read` fields that force 23 casts to `any`, an `openedPlacedId` memory repaired after every request, and station records made lazily. Every replacement was run against the project's own tests in memory with no file written, but none has been through the formatter, the linter or the strict type checker.
