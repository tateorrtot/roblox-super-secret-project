# Review of Architecture Draft 3, November 2026

Compiled 2026-11-18. Draft 3 of the architecture note was written to answer the review of draft 2 ([09-architecture-review-draft2.md](09-architecture-review-draft2.md)). Four agents then checked it: one per original review lens, each deciding whether every earlier finding was closed and listing any problem draft 3 introduced, and one cold reader who had seen no earlier draft or review. Their findings were not sent to a referee.

**All four said they would not approve draft 3.** None found a reason to change the six-directory shape or the kernel-plus-features split. The three lens agents each said what remained was about a page of sentence and table fixes. The cold reader found 37 problems, two of them blocking.

Section numbers in this file refer to draft 3, whose numbering differs from draft 4's.

## What all four found
- **Opening a container was an action in three sections and "not an action" in a fourth.**
- **The rule for one feature reacting to another was broken by the note's own example,** and nothing said what happens when something fails after the first change.
- **Two of the four first-build features had no server glue or client view,** and the state "lit" belonged to one feature while another feature's view drew it.
- **The step table and the module tables did not match,** and several modules were in neither.
- **The kernel table left out things the rest of the note had the kernel hold.**

## What draft 4 did about it
Draft 4 fixes those contradictions, and it also changes what the note claims. Hand-written tables of which module requires which were incomplete in all three drafts, so draft 4 drops them: a tool prints that graph from the code. It separates what the user is asked to approve (the shape, the rules, the decisions that are expensive to change) from a provisional plan, and it carries eleven game-rule questions to the user where earlier drafts had assumed answers.

## Problems draft 3 introduced

### The listener rule contradicts its own example, and signals inside an action are not squared with 'no rollback' (major)
- **Where:** Section 2 'How a change is reported' (points 1, 3, 4); section 3 'Call down, signal up', 'A listener cannot refuse' and the lit-station paragraph
- **Problem:** The rule says a listener 'changes only its own feature's state'; the example has stations' listener 'tell `climate` to remove the heat', which changes climate's state. So the note does not say whether a listener may call down or dispatch, and three things follow. (a) Whatever it calls validates and may refuse, while a listener 'cannot refuse' and there is 'no rollback'. (b) A listener runs in the middle of the firing handler; if it may change state of features at or before the one that fired, it can undo what that handler validated before its 'first change'. (c) 'An action dispatched from inside a handler runs at once' can likewise refuse after the outer handler has changed something, and `World` fires only if 'the outermost handler returns ok', so changes already made would never reach projectors and senders. Listeners also change state without validating and without being registered with `Actions`, which loosens the owner's rule that all changes go through one code path. The mechanism is consistent only under a narrower rule than the one written.
- **Suggestion:** State it in three sentences, for example: signals fired during an action are delivered when the outermost handler has made its last change, in install order, before `World` fires; a listener writes its own section and may call only functions that cannot refuse (this covers the climate example); a handler calls or dispatches anything that can refuse only before its own first change. Have `Actions` fail the test run when an action refuses after a record was reported.

### Opening a container has no path that fits the rest of the note (major)
- **Where:** Section 7 'The wire', against sections 2 (Buttons, Access), 3 (button meanings), 5 (Intake, inventory/Sender), 10 and 23 item 5
- **Problem:** Section 7 says opening is 'a subscription held by the sender, not an action, because it changes nothing in `World`'. But a feature states 'Use on a thing with a `container` part opens it', a tap goes 'server/Intake -> rules/Buttons -> action', and `Buttons` 'Turns the player's two buttons into an action'. So either Buttons returns something that is not an action, or opening is one. The consequences are not small. `Access` is asked only by handlers, so the proposed rule 'anyone can open a container' has nowhere to be decided. The open state lives only in glue, so the `MoveStack` handler cannot check that the actor has that container open. The sender must end the subscription when the player 'walks out of reach' but requires no `Index`. And if the client asks the sender directly, a per-feature module validates client input outside `Intake`, against invariant 10 and section 24's 'so `Intake` checks every one'.
- **Suggestion:** Make Open an action that changes no state: its handler asks `Access` and reports one record, 'opened by this actor', and the sender starts the subscription on that record; closing stays in glue. Say where reach is checked for a panel request (for example, the registered shape marks which fields are targets and `Intake` checks reach to each).

### The first build's own tables break the per-feature glue rule for stations (major)

State the rule: several features may decorate one Instance through `Index` and `Things`, each from its own files.
