# Review of Architecture Draft 2, November 2026

Compiled 2026-11-18. Three reviewers each read draft 2 of the architecture note through one lens, and a referee then tried to refute every finding they rated blocking or major. Minor findings were not checked by a referee.

**All three reviewers said they would not approve draft 2.** The referees upheld about 45 of the serious findings, three of them as blocking. Draft 3 of [07-architecture.md](07-architecture.md) was written to answer them; its section 22 maps findings to changes. This file is the record of what was found, kept so the reasoning behind draft 3 can be checked.

Where a finding quotes a section number, it means draft 2's numbering, which differs from draft 3's. Draft 2 called the rules directory `game`; draft 3 renames it `rules`.

## What held
- The six-directory shape with one-way dependencies.
- Relative requires are fully released in Roblox with no setting, and resolve from the script's parent.
- Rojo 7.7.1 accepts one directory mapped to two places.
- The no-Roblox-globals type check behaves as described.
- The statements about the Input Action System, ProfileStore, Server Authority and data store limits matched current sources.

## What failed
- **Nothing let one feature react to another,** so "adding a feature must not edit another feature's files" could not hold. The first case arrived inside the first build.
- **Two first-build features each needed the other** (`stations` and `climate`), which the ordering rule forbids.
- **The kernel's `Defs` module held every feature's definition types,** so the kernel knew the features and each new one would edit it.
- **How `World` learns of a change, and what it tells listeners, was undefined,** although every handler and both server listeners are written against that contract.
- **Content could not both require nothing and be checked by strict typing.** Reproduced with the pinned tools.
- **The client could not reach `lib` and `protocol`** with the layout as drawn. Reproduced with the pinned tools.
- **The streaming claim depended on place settings the note never listed.**
- **Saving had no rule for a document newer than the server.**
- **The "can it be added" table priced rule code only** and rested several rows on features that are not designed.
- **Milestones 2 to 4 were several changes each.**

# A. Coupling and growth

**Would approve draft 2:** no

I would not sign this as it stands. The note claims more than the design delivers: two of its own first-build features need each other, nothing lets one feature react to another, and the kernel file Defs plus seven or so shared glue files are edited by every new feature. Several rows of §7 also rest on systems the note itself says are not designed. The honest answer to "can it be added" is yes for each of the owner's examples, as a new feature plus a known set of shared-file edits, with three exceptions that need a decision before code: building on anything but a plot, state for an owner who is offline, and reactions across features. Most of the fixes are changes to the text and the tables, not to the overall shape.

## Findings the referee checked

### 1. First build: stations and climate each need the other, which the ordering rule forbids
- **Upheld, major.** Confirmed in the note's text; lowered from blocking. §3 has climate handle conditions 'given off by places and running stations' but lists only 'Kernel, building' as requirements, so a station's running state has no declared source. In the other direction lib/Recipe takes 'which conditions hold', Recipes.luau holds 'what it needs', and §7 prices a recipe responding to mana as data only, so stations has to ask whichever feature holds conditions; that feature is listed after it and arrives at milestone 7, which §2 forbids ('never one listed after'). The kernel has no part through which a later feature can feed an earlier one, so I found no reading that makes both directions legal. Nothing else in the four first-build features consumes a condition (bodies are under 'none of it designed yet'). Lowered because reordering two rows and two milestones removes the cycle with no new mechanism, and no code exists yet.
- **Fix proposed:** List climate before stations in §2, §3 and §17 (swap milestones 5 and 7, or merge them). Climate keeps the list of sources and answers 'what holds at this tile' and never reads stations. Add climate to stations' Requires cell and say that stations tells climate when a station starts or stops giving something off, and asks it which conditions hold before a recipe runs. Say in the milestone that a recipe is what consumes a condition in the first build.

### 2. Nothing lets one feature react to another, so 'must not edit another feature's files' cannot hold
- **Upheld, blocking.** Confirmed, with two parts overstated. The only links between features in §2 are 'require the kernel and features listed before it' and one handler per action kind (Actions row). No rule covers an earlier feature whose behaviour depends on a later one (finding 1 is a first-build case; a station that needs power is a later one). Nothing says whether a feature may connect to World's change signal, what a listener may do, or whether a dispatch made inside another handler nests or queues. §7 contradicts itself in adjacent lines: level 2 is 'a small handler inside an existing feature', then 'None of them should edit an existing feature'. Overstated: for a later feature hearing an earlier one, World's 'one signal for every change' is a usable mechanism that the note simply never gives to features; and the lightning example is answered by the proposed per-people response tables (data read by one handler), not by several handlers. Kept at blocking because this is the promise the owner's 'can it be added' test rests on, the dispatch rule shapes every handler from milestone 2, and the first case arrives at milestone 5: breaking a running station leaves stations holding state that building, listed earlier, cannot tell it about.
- **Fix proposed:** Add to §2's rules: 'Call down, signal up. A feature may call features listed before it. So that later features can react, a feature exposes its own signals (lib/Signal) and, where its behaviour must be extended, its own registration points; a later feature connects in its install. An earlier feature never names a later one. A listener changes state only by dispatching one of its own actions', and say whether that dispatch runs nested or after the current action ends. Reword the promise to: 'Adding a feature must not put knowledge of it into another feature's files. An existing feature may gain a generic signal or registration point, as its own small change, when the first feature that needs it arrives.' In §7 replace 'None of them should edit an existing feature' with 'Levels 1 and 3 edit no existing feature; level 2 is a small addition inside one.'

### 3. game/Defs.luau holds every feature's definition types, so the kernel knows the features and each new one edits it
- **Upheld, major.** Confirmed in the text; lowered from blocking. §1 says 'game/Defs.luau declares the types and holds a registry' and the Defs row repeats it, while the content table gives a placeable a footprint (building's concept), slots (inventory's) and 'recipes it runs' (stations'). So a kernel module does name feature concepts, against 'The kernel knows nothing about any particular feature', and a feature with a new kind of definition or a new field has to edit Defs.luau, which §2's 'What adding a feature touches' does not list. The remark that a crate is described in two content files is an observation, not a defect. Lowered because it is one wrong sentence and one unlisted shared-file edit; moving the types later would not touch saves or the directory graph.
- **Fix proposed:** In §1 and the Defs row say: 'Defs holds only the registry and the lookup. Each feature declares the type and Schema shape of its own kind of definition, or of its own fields on a shared kind, in its own directory and registers them in install.' Add 'its definition types' as a sixth thing a feature may provide, and add it to 'What adding a feature touches'.

### 4. content cannot both 'require nothing' and be checked by strict typing
- **Upheld, major.** Reproduced with the pinned luau-lsp 1.70.1 (--platform=standard, solver flag each way) on copies of the reviewer's probes and one of my own, in (session scratchpad) Valid content handed to a typed Defs function is rejected at the hand-off line when keyed by id (both solvers), as an array on the new solver, and as an array on the old solver when no row carries every optional field. With 'read' fields the new solver accepts a valid array but reports one of three faults, in the entry script and not at the row; 'read' is a syntax error on the default (old) solver. My probe q1 adds that a cast at the hand-off is accepted silently for a missing and for a wrongly typed field on both solvers, so a cast does not rescue the claim. Annotating the table inside the content file gives row-and-column errors on the new solver, but that needs a require of the type: luau-lang/luau issue 452 (a require only for types) is closed as not planned. The grounding's own advice ('assigned to an annotated local') already assumed such a require. One nuance: the old solver does accept a valid array when some row has every optional field.
- **Fix proposed:** Change content's 'May require' cell in §1 to 'the game modules that declare its definition types, for the types only', add the content-to-game arrow to the diagram and to the edge check, and annotate each content table (there is no cycle, because game never requires content). If 'requires nothing' is to stay, replace 'Strict typing catches a missing or wrongly typed field' with 'The type checker does not check content; Defs takes it untyped and Schema is the only check, in the tests and at server start.' Decide it together with the solver choice in milestone 1.

### 5. Rules are split by feature but the Roblox glue is not, so each feature edits the same shared files
- **Upheld, major.** Confirmed in the text. 'What adding a feature touches' lists protocol message types and one client view but none of Intake, Broadcast, Projection or Mirror. Those are one module per role and are described in terms of the first two features ('their inventory and any container they have open'; 'placed things and items on the ground'). Inside the first build, stations already needs Projection to show a lit station, and building needs Broadcast and Mirror for the crate panel. Overstated in one respect: the rule 'must not edit another feature's files' is not broken, because glue is not a feature, and a feature that only uses the two verbs on existing kinds of thing adds no glue. The stated cost list is still incomplete, and these are the files that would gain a branch per feature.
- **Fix proposed:** Extend §2's 'What adding a feature touches' with the glue it omits: Intake and protocol/Intents for a new intent; Broadcast, protocol/Updates and Mirror for new per-player state; Projection for a new kind of visible thing; the wiring in Main.client. If a branch per feature in those files is not wanted, say instead that each is a generic mechanism and a feature brings its own projector, sender and view as new files wired in the two entry scripts, with one protocol file per feature.

### 6. Any module holding World can read every feature's state by name, and the require check cannot see it
- **Upheld, major.** Reproduced: the reviewer's probe p4 passes strict analysis with exit 0 on both solvers despite a misspelled field, a misspelled section name and a misspelled action kind with the wrong payload. That result depends on the probe typing a section as 'any'. In my probe q2 (same verify-cg folder) a lookup that returns 'unknown' plus a typed accessor exported by the owning feature turns the same typos into errors on both solvers and puts the edge in the require graph. The note does not say which it is: its install example names sections and action kinds by string, and its Requires cells give Projection and Broadcast only game/World although they must know the shape of building's and inventory's state. The edge check in §1 walks require calls, so it cannot see this coupling, which is the coupling the owner asked to be able to see.
- **Fix proposed:** Add to the World row: 'World's own lookup returns an untyped value. A section is read only through a typed function exported by the feature that owns it, such as Inventory.state(world), and an action is dispatched only through a typed function of its feature, so every such use is a require edge and a typo is a type error.' Correct the Requires cells: Projection requires building and inventory; Broadcast requires inventory.

### 7. How a change becomes a signal is not designed, and it decides whether Projection and Broadcast can stay generic
- **Upheld, major.** Confirmed in the text. World 'fires one signal for every change', state is 'plain tables' (invariant 8) that handlers change, and nothing says how World learns of a change, what a change record holds, which module declares it or who may listen. 'Ledger' appears once, in the Actions row, with no reader, purpose or size limit, against §14's 'No future-proofing'. The cycle warning is a hazard and not a defect in the note as written, where Actions requires World and not the reverse. The facts behind it hold: probe p3 fails on both solvers with 'Cyclic dependencies are only supported if all modules in the cycle use export syntax'; luau.org's type-checking page says cyclic module dependencies cause problems for the checker; Roblox's ModuleScript page gives the run-time error 'Requested module was required recursively'.
- **Fix proposed:** In the World row say how a change is announced (for example: handlers change state only through World's own functions, each of which fires the signal with one record), give the record's type and declare it in World so that Actions can name it without a cycle, and say who may connect (glue only, or features too). Give the ledger a reader and a size limit, or delete the word until a milestone needs it.

### 8. §4's channels miss events, area-wide state, other players' held items and moving things; the attribute format is an undeclared protocol
- **Upheld, major.** Three of the five parts are confirmed and reach the first build; two concern features the note defers. (a) HeldView requires Mirror, and Mirror holds what Broadcast sent that player (their own inventory), so nothing shows what another player holds; Roblox's remote-events page confirms an Instance created on a client is not replicated across the boundary. (b) Updates is defined as state and Mirror as a copy, so a hit or a break has no stated path, and the streaming page says a streamed-out instance is parented to nil, so a client cannot read 'broken' from a removal. (c) The entity id and the 'display copy' attributes are read by Input and by WorldEffects ('Nothing of ours') by name, outside protocol and outside the require graph. The attributes page confirms that a property change may arrive before or after a remote. Area-wide state such as weather, and moving server-owned things, belong to features §15 says are not designed; they need a line, not a design. The claim that the first build 'needs' events for hit and break is a little strong, since an attribute change could carry some of it.
- **Fix proposed:** Add rows to §4: one-shot events (a hit, a break, a recipe finishing) sent by remote with entity ids; what another player is holding (name the channel); and one line each for area-wide state such as weather and for moving server-owned things, marked as not built. Put the attribute and tag names used on projected Instances (the entity id, 'lit') in protocol and list Projection, Input and WorldEffects as requiring it. Retitle §4, since there are more than two channels.

### 9. No seam brings engine-owned facts into the rules, or takes non-model results out
- **Upheld, major.** Confirmed. Rules are pure and placed state is plot-local tiles; §11 keeps movement client-simulated (Roblox's security page: the server 'cannot necessarily always control the player's character'), so where a character, creature or vehicle is never enters World, and no server module is given the job of supplying it. In the other direction WalkSpeed is a Humanoid property on Roblox's reference page, and the note names no module that may write to a character. The reviewer's first-build example (cold affecting a player) is conditional, because the first build has no bodies. Milestone 7 has its own case, though: where 'a cold place' lies relative to plot tiles is a fact of the authored map or of Plots, and climate (pure, requires 'Kernel, building') has no way to receive it. Intake's reach check also needs Plots or Projection, which its Requires cell omits. The reviewer accepts that the seam need not be built before a milestone uses it.
- **Fix proposed:** Name the seam the way Clock is named: one injected source, implemented in server glue and faked in tests, that answers 'where is this entity', 'who is in this area' and, for milestone 7, 'which place is this tile in'; and one named server module that may write to characters. Show both in §6 and add a row to §5: 'Positions of characters and vehicles: changing, owned by Roblox, not in World'. Add Plots to Intake's Requires cell. Say each is built when a milestone first needs it.

### 10. The client may not require content, but it needs footprints, recipes and whether an item can be placed
- **Upheld, major.** Confirmed in the text, with the need itself a design inference. §1 says client must never require content, and presentation holds 'id to icon, sounds and effects' only. Placing a multi-tile thing by touch needs a preview drawn from its footprint and from 'whether it can be placed', and a station panel needs a recipe's inputs and outputs; all of that is in content. The note does not say which route it takes: a copy in presentation (two sources that can drift, with no cross-check possible), definitions sent through Updates, or content shipped to clients. The note never mentions a placement preview, so the first build could run without one, but the question arrives at milestone 4 and the answer changes the directory table the owner is asked to approve. §4's grey-box fallback would also hide a missing model, as the reviewer says.
- **Fix proposed:** State in §1 how the client gets the definition facts it must show before the server answers. The smaller option: add content to the directories copied to ReplicatedStorage and to client's 'May require' cell, since content is data and only game needs to stay on the server. Otherwise say Broadcast sends the needed definitions with the first snapshot and add them to the Updates row. Add a test that every content id has a presentation entry and a model, or is on an explicit grey-box list.

### 11. What blocks, what can be tapped and what is in reach come from the art model, not from the definition
- **Upheld, minor.** Confirmed as a gap; lowered from major. §4 has the server clone the art model as the thing in the world and never says what collides or what a tap hits. Roblox's collisions page ties physical collision to each part's CanCollide and says CollisionFidelity 'determines how precisely the physical bounds align with the visual representation'. So swapping art can change what blocks and what is tappable while, as the note says, 'no rule' changes. That touches the owner's rule that visuals are not tied to logic. Lowered because Projection can impose either answer in code at clone time whenever it is chosen, with no change to rules, saves or the graph, and the grey-box build is footprint-sized anyway. The reach part is conditional on reach being measured to the Instance, which the note does not say.
- **Fix proposed:** Add to §4: 'What blocks movement and what a tap can hit come from the definition, not the art. Projection builds the solid, tappable shape from the footprint and parents the art inside it with collision and queries off; a definition that needs another shape (a doorway, stairs) says so in data.' If the art is to be authoritative instead, add a check that each model's bounds match its footprint.

### 12. building and the save format assume a plot is the only grid, against an agreed design decision
- **Upheld, major.** Confirmed, with the title overstated. The building row places things 'on a plot's grid', §9 and §16 fix 'plot-local' tile coordinates, and the grounding's own check (section B, 'What the brief missed', item 7) said this 'needs an answer before the first save ships'; the note lists the convention as expensive to change and gives no answer. The project notes on disk do record 'Vehicles and large creatures are platforms you build on' as agreed and 'things can be set down anywhere' as proposed. Also confirmed: invariant 1 names 'on the ground' as a place a stack can be, but no section says what coordinates a ground item has or whether it is saved, and the first build needs that at milestones 3 and 6. Overstated: the note does not go against the agreed decision, it defers vehicles (§15), and a deck could later be saved as a second list beside the plot's without changing any existing tuple.
- **Fix proposed:** In §9 and §16 write: 'Coordinates are local to a grid. Today the only grid is the plot; a deck would be saved as another grid with its own list, so existing tuples do not change.' Change the building row to 'on a grid (today a plot's)'. Add one sentence saying what position an item on the ground has and whether it is saved with the plot.

### 13. Loading and unloading a player's things has no stated path, and saved references between features are undefined
- **Upheld, major.** Confirmed in the text. Main.server builds one kernel and one World per server, while §9 saves 'one document per player', so export and import act on one owner's slice of a shared World. A feature's five provisions include export and import but no unload, so nothing removes a leaving player's things. importState is not an action handler, although the Actions row says 'Nothing else changes World' and invariant 2 says only handlers do. Nothing says how saved sections refer to each other (a crate's tuple is building's, its contents are inventory's), given that World hands out entity ids per session, and the plot tuple's 'then any state' leaves it open. Nor does the note say where migration steps live for a document with one version number and a section per feature. These decide the save format, which §16 itself lists as expensive to change. The point about import order is inference.
- **Fix proposed:** Describe join and leave in §9: loading a player is an action (or state the exception to invariant 2 and to the Actions row) that merges that player's sections into World and fires the same change signals; add 'unload' to what a feature provides, so a leaving player's things are removed. Say how one saved section refers to another (for example by a placed thing's index in the plot's tuple list, never by a session entity id). Say where migration steps live.

### 14. State that does not belong to an online player is outside the save design, so offline shops and shared sites are not additions
- **Upheld, minor.** Partly refuted; lowered from major and narrowed. Confirmed: §9 covers only one document per player, and ProfileStore's API page documents MessageAsync to a profile with no session but no update across two profiles. Not confirmed: that shared sites 'are not additions'. A per-site document is a second key and a second small store beside the player document (ProfileStore keys are plain strings; the grounding recommends one DataStore key per site), and it changes nothing on §16's list. Offline shops are not in the owner's agreed list, and plots that leave with their owner are the owner's own choice. The region pass-through case arises only if a place skips importing a section, which the note does not say it does. What remains is one missing sentence about an agreed later addition, shared world state at fixed sites.
- **Fix proposed:** Add to §9: 'State that belongs to a site and not to a player (a community goal, a settlement's supply) is not in this document. When it arrives it is a second kind of document with its own key, read and written through the same save-store interface, which therefore takes a key and not a player.'

### 15. Verbs decides by registration order, and the feature order in Main.server silently controls five behaviours
- **Upheld, major.** Confirmed for the core claim. The Verbs row says 'the first that recognises the target wins' and §2 installs features in dependency order, so the earlier, more general feature always wins. A station is also a placed thing with slots, so the resolver that opens a container (milestone 4) takes Use on a station before stations (milestone 5) is asked, and stations cannot change that without editing an earlier feature or an install order that the require rule fixes. Also confirmed from the directory rules: protocol requires nothing and game may not require protocol, so a panel request such as moving a stack is declared twice and mapped by hand in Intake. The note never says whether one feature changes another's state by calling its functions or by dispatching its actions. Overstated: tick, import and listener order are not stated in the note at all, so 'five behaviours' is partly inference; and 'one held thing meeting one target' is listed in the project notes as proposed, not as the owner's rule.
- **Fix proposed:** Change the Verbs row to: 'A resolver is registered for a kind of target, and optionally a kind of held thing. The most specific key wins, and two resolvers for the same key is an error at start-up.' Add one sentence to §2's rules: 'A feature changes another feature's state by calling that feature's exported functions, never by dispatching its actions by name' (or the reverse). Say that a feature marks which of its actions a client may request and supplies the validator, so Intake holds no per-feature mapping.

### 16. The kernel is a small plugin framework, not only registries, and nothing keeps it small
- **Upheld, minor.** Two parts are confirmed from the text; lowered from major because the rest is a label or is avoidable. Confirmed: a feature may provide 'a tick' and Loop 'calls each feature's tick', but none of the five kernel parts holds ticks and the install example registers none; and what a handler receives is never stated. Not a defect: 'framework' is a label, and the note promises only that there is no heavy one. 'Nothing keeps it small' overlooks the project rule that a core change past a few hundred lines stops for a plan, and §14's 'No future-proofing'. The cycle argument is avoidable: in my probe q2 a handler that closes over the kernel at install type-checks on both solvers with no edge from Actions to Kernel. Untyped string kinds are finding 6.
- **Fix proposed:** Say where a tick registers: name the kernel part, or say Main.server hands each feature's tick to Loop. State a handler's parameters, and that it reaches Defs through the kernel it captured at install. Optionally add: 'A new kernel part needs the owner's sign-off.'

### 17. §7 prices only rule code and leaves out prerequisites, so most costs read lower than they are
- **Upheld, major.** Confirmed against the table. The three levels are defined only as data, a handler in an existing feature, or a new feature directory; none counts glue, a client view or a new channel. Only the vampire row names what must exist first. Mud, thunder, boom rats and wolfmen are priced at 2, 'a small handler inside an existing feature', but the features they would sit in (bodies, peoples, creatures) are under §2's 'none of it designed yet'. 'Ice cave: 1' needs a way to say where a place is, and the content table has only Items, Placeables and Recipes, with no module that reads the map. '1 per region' is no code but a whole Roblox place (§8). The carrier rows rest on what §15 says is not designed, and the project's transport research (docs/06) lists flying creatures as 'shipped but demanding' with an air controller last, not as a small handler. The walkthroughs the reviewer cites are theirs and are not in the note; the finding stands without them.
- **Fix proposed:** Say above the §7 table that the three levels count rule code only. Add two columns, 'needs first' and 'glue and client', and mark every row that rests on a feature from §2's 'none of it designed yet' list as an estimate. Replace the closing sentence with: 'Each example can be added as data, or as a new feature plus a stated set of shared-file edits, once the features it stands on exist.'

### 18. Who is acting, and who may do what to whose things, is not part of an action
- **Upheld, major.** Confirmed by absence. The note never says who is acting or who may act on whose things: the Actions row says a handler 'validates', Intake checks only shape and reach, and the shape of an action is not given, although §2 says stations 'issues an action like any player would' and a server holds several players' plots from milestone 4. The project notes record 'Any step can be done by you, an NPC or a friend' as part of the confirmed core, so an 'owner only' check written into each handler would have to be edited in every feature when friends or helpers arrive. One thing the reviewer's fix misses: inventory is listed before building, so a rights function owned by building could not be called from inventory's handlers under the ordering rule.
- **Fix proposed:** Add to the Actions row: 'An action is a kind, an actor (a player, a helper or the system) and a payload. Intake sets the actor from the sender, never from the message.' Add: 'Whether an actor may act on a thing is answered in one place that every handler calls (a small kernel part, or a feature listed before all the others), never written into a handler.'

## Minor findings (not checked by the referee)

### Edges, modules and one cycle risk missing from the tables
- **Where:** Module tables in §2 and §3; invariant 5 ('A client sends intents and nothing else')
- **Problem:** No cycle exists among the Requires cells as listed. Three are implied by the stated jobs: stations and climate; World and Actions if the change record type lives in Actions; Kernel and any of Actions, Verbs or Save if a handler is typed with the Kernel. Unlisted edges: presentation/Items and presentation/Placeables are required by no module, though HeldView, Hotbar, ContainerPanel and WorldEffects need them; Projection requires Plots (tile to world position); Intake requires Plots or Projection for reach; Kernel requires lib/Clock and lib/Random; Verbs probably requires Actions for the action type; Main.server requires game; Defs either imports the recipe and footprint shapes from lib/Recipe and lib/Grid or declares them a second time. Modules with no row: the save-store interface, the ProfileStore adapter and where the vendored file sits (it is outside the six directories), the in-memory store, the real clock, and whoever owns the remote objects. The first-snapshot request is a client message that is not in the Intents list. tests/ is not in the dependency table. client cannot reach lib and protocol by relative require, because './' is script.Parent and '../' is script.Parent.Parent and by the note's own placement they are not siblings; so the client's require style is unstated, and the grounding shows Lune resolves neither '@game' nor script paths, which means Mirror's logic cannot be loaded by the test runner.
- **Suggestion:** Complete the tables, or better, generate them from the require walker so they cannot drift from the code.
- **Source:** https://create.roblox.com/docs/reference/engine/globals/LuaGlobals

### The mechanical check is per directory; the rules that prevent a spider web are per module
- **Where:** §1 ('fails on any edge not in the table'); §2 feature rules; §3 ('Views never talk to each other and never send intents. Input never reads a view.')
- **Problem:** The table has six rows. Feature order, edges between server modules, and the client rules about views and Input all live inside one directory, where the check as described sees nothing. The module tables that would catch them are prose in a markdown file.
- **Suggestion:** Let the walker read a small data file of allowed edges at feature and module level, and print the graph from the same file. That also gives the owner the picture he asked for, always current.

### The note's own 'and' test fails on several rows
- **Where:** §14 ('If a module's description needs the word and, it is probably two modules')
- **Problem:** World (holds sections, hands out ids, fires change signals); Defs (types and a registry); Actions (routing and a ledger); Save (collects sections and runs migrations); Intake (receives, checks shape, checks reach, routes); Plots (assigns a spot and converts coordinates); Input (two buttons, the hotbar, aiming, sending, while the hotbar also appears as ui/Hotbar); stations (advancing and catching up).
- **Suggestion:** Split the ones that are hubs (World, Intake, Input), or reword the convention so the page that states it does not break it.

### Things built before a milestone needs them
- **Where:** §14 ('No future-proofing. A field or module is added when a milestone needs it.'); §1 ('lib, protocol (a second copy of the same files)')
- **Problem:** lib/Random and the kernel's seeded random source (no first-build feature is described as using chance); the clock in the kernel at milestone 2 (its first user is stations, milestone 5); the Verbs registry with a single resolver until milestone 4; the ledger (no reader); the 'which conditions hold' input of lib/Recipe two milestones before anything gives off a condition; and the second copy of lib and protocol so that rule code is hidden from clients, which guards against a problem not yet shown and adds a second place to look in Studio. ### Godot-to-Roblox table: seven rows would mislead a Godot developer
- **Where:** Section 19, the table (lines 387-403)
- **Problem:** (1) '_process, _physics_process | RunService.RenderStepped, Heartbeat': RenderStepped 'has been superseded by PreRender', and Heartbeat 'fires every frame' with a varying delta; it is not a fixed tick.
